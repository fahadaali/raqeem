# المرحلة الثانية — طبقة الـ SaaS

هذا الدليل يشرح ما بُني من البنود التي **أجّلتها وثيقة المتطلبات عمداً** إلى المرحلة الثانية،
وكيف يُشغَّل كلٌّ منها.

نصّ التأجيل في المقدمة الاستراتيجية للوثيقة:

> «جيل واجهات الـ SaaS: في هذه المرحلة لا يُطلب من الفريق البرمجي بناء واجهات التسجيل الآلي
> للمدارس الجديدة (Onboarding)، أو خطط الأسعار والاشتراكات (Pricing Plans)، أو الدفع لرسوم
> الرخص المستهدفة (Billing System).»
>
> «لوحة التحكم الموحدة (Super Admin UI): في هذه المرحلة تكون لوحة التحكم العليا مخصّصة لمدير
> الجهة التعليمية/المستأجر رقم ١ لإدارة فروعه فقط، ولن يتم بناء لوحة تحكم مالك الـ SaaS
> (التي تدير الجهات المختلفة) إلا في المرحلة الثانية.»

الأربعة كلها مبنيّة الآن، والأساس المعماري لم يتغيّر: `tenant_id` إلزامي، وفلترة الاستعلامات
الشاملة كما هي، وشيفرة واحدة تخدم كل الجهات.

---

## ١. مفتاح التشغيل — طبقة قابلة للإطفاء

الطبقة تُشحن **معطّلة افتراضياً** (`saas_enabled = 0`)، فتعمل المنصة تماماً كما في المرحلة
الأولى: مستأجر واحد، بلا صفحة أسعار ولا تسجيل ذاتي ولا شاشة اشتراك في القائمة الجانبية.

يفتحها مالك المنصة من **لوحة مالك المنصة ← إعدادات المنصة**:

| المفتاح | الأثر |
|---|---|
| `saas_enabled` | يُظهر صفحة الأسعار وهوية المنصة وشاشة الاشتراك للجهات |
| `signup_enabled` | يفتح التسجيل الذاتي `/signup` |
| `signup_needs_review` | يجعل كل طلب تسجيل ينتظر اعتماد المالك بدل التفعيل الفوري |

إطفاء المفتاح يعيد المنصة لوضع المستأجر الواحد فوراً دون فقد أي بيانات.

---

## ٢. لوحة تحكم مالك المنصة `/platform`

الطبقة الوحيدة في المنصة التي **تتجاوز عزل الجهات**، ولذلك:

* لا تكفي فيها صلاحية «مدير الجهة» — يلزم علَم `is_platform_admin` على الحساب.
* كل عملية فيها تُكتب في جدول `platform_logs` **المقفل ضد التعديل والحذف** بمُشغّلات قاعدة
  البيانات، تماماً كسجل تدقيق الجهات.
* في التهيئة الأولى يُمنح العلَم لمدير الجهة رقم ١ (استمراراً لما نصّت عليه المرحلة الأولى).

### التبويبات

| التبويب | ماذا يفعل |
|---|---|
| **نظرة عامة** | الجهات · الإيراد الشهري المتكرر (MRR/ARR) · المحصّل والمستحق · الاستخدام الكلي · ما ينتظر إجراءً |
| **الجهات** | بحث · إنشاء جهة · تعديل الهوية والنطاق · إيقاف وتفعيل · تغيير الخطة · إصدار فاتورة · دخول إداري · محو كامل |
| **الخطط** | إنشاء وتحرير وحذف خطط الأسعار وحدودها ومزاياها |
| **الفواتير** | كل فواتير المنصة · اعتماد إشعارات السداد · تسديد أو إلغاء الفواتير |
| **طلبات التسجيل** | اعتماد أو رفض طلبات الجهات الجديدة عند تفعيل المراجعة اليدوية |
| **إعدادات المنصة** | الهوية · مفاتيح الطبقة · الضريبة والعملة والبيانات البنكية · مالكو المنصة |
| **سجل المنصة** | كل ما فعله المالك، بحثاً وتصفية — مقفل ضد التعديل |

### الدخول الإداري للمساندة

`POST /api/platform/tenants/:id/impersonate` يصدر جلسة قصيرة بحساب مدير الجهة، ويُسجّل الحدث
**مرّتين**: في سجل المنصة، وفي سجل تدقيق الجهة نفسها بوصف صريح «دخول إداري من مالك المنصة»
حتى يراه مدير الجهة في شاشته. الجلسة بلا رمز تجديد فتنتهي بانتهاء صلاحيتها.

### محو جهة

عملية لا رجعة فيها تتطلّب كتابة رمز الجهة للتأكيد. تمحو الصفوف عبر `ON DELETE CASCADE`،
وتنظّف مجلّد الجهة في التخزين، وتُبقي **أثر المحو نفسه** في سجل المنصة مع إحصاء ما مُحي.

سجل التدقيق مقفل ضد الحذف بمُشغّل مشروط:

```sql
CREATE TRIGGER trg_audit_no_delete BEFORE DELETE ON audit_logs
WHEN (SELECT COUNT(*) FROM tenants WHERE id = OLD.tenant_id) > 0
BEGIN SELECT RAISE(ABORT, 'AUDIT_APPEND_ONLY'); END;
```

أي أن صفاً منفرداً لا يُحذف أبداً ما دامت جهته قائمة، ولا يسقط السجل إلا تِبعاً لمحو الجهة
كاملةً — وهو ما يوفّق بين شرط «Append-only» في البند ١٤ وحقّ المحو في نظام حماية البيانات الشخصية.

## ٣. خطط الأسعار

الخطط **بيانات لا شيفرة**: جدول `plans` يحمل السعر الشهري والسنوي وأيام التجربة وثلاثة حدود
(الفروع، المستخدمون، التخزين) وقائمة مزايا تسويقية. تغييرها من اللوحة يغيّر صفحة الأسعار فوراً.

الخطط الافتراضية المعبّأة:

| الخطة | الشهري | السنوي | الفروع | المستخدمون | التخزين |
|---|---|---|---|---|---|
| الأساسية | مجاناً | مجاناً | ١ | ١٥ | ٥١٢ ميجابايت |
| النمو | ٤٩٩ ر.س | ٤٩٩٠ ر.س | ٨ | ١٢٠ | ١٠ جيجابايت |
| المؤسسية | ١٤٩٩ ر.س | ١٤٩٩٠ ر.س | بلا حدود | بلا حدود | بلا حدود |

**تطبيق الحدود** يقع قبل الكتابة لا بعدها، في ثلاث نقاط: إنشاء فرع، إنشاء مستخدم، رفع ملف.
تجاوز الحدّ يعيد `403 QUOTA_EXCEEDED` مع تفاصيل الحدّ والاستهلاك الحالي، فتعرض الواجهة دعوة
للترقية بدل رسالة خطأ عامة. ولا يُحذف شيء عند بلوغ الحدّ.

**التخفيض** إلى خطة أضيق من الاستهلاك الحالي مرفوض صراحةً، وتُعلّم الخطة في الواجهة بأنها
غير قابلة للاختيار مع بيان سبب المنع.

## ٤. التسجيل الآلي `/signup`

ثلاث خطوات في صفحة واحدة: بيانات الجهة ← حساب المدير ← الخطة. مع فحص فوري لتوفر رمز الجهة
والبريد أثناء الكتابة، ورفض الرموز المحجوزة (`ADMIN`, `API`, `WWW`, …).

عند الإرسال يجهّز `provisionTenant()` الجهة كاملةً في عملية واحدة:

1. كتالوج الصلاحيات (٦٠ صلاحية)
2. المستأجر بهويته وإعداداته
3. الأدوار العشرة بصلاحياتها
4. الفرع الأول والفصل الدراسي الجاري
5. حساب مدير الجهة
6. الاشتراك بفترته التجريبية

ثم يُسجَّل الدخول تلقائياً — الجهة جاهزة للعمل خلال ثوانٍ.

مع تفعيل `signup_needs_review` يُحفظ الطلب في جدول `signups` (بكلمة مرور مجزّأة، لا نصية)
وينتظر اعتماد المالك، فلا تُنشأ الجهة قبل الاعتماد.

## ٥. نظام الفوترة

### دورة الحياة

```
تسجيل ──▶ trialing ──(انتهاء التجربة)──▶ past_due ──(سداد)──▶ active
                │                            │                   │
                │                     (انتهاء المهلة)      (نهاية الفترة)
                │                            ▼                   ▼
                └──(إيقاف التجديد)──▶ expired          فاتورة تجديد ──▶ past_due
```

الوظيفة اليومية `subscriptions` (مؤقّت Cron `0 1 * * *`) تدير هذا كله:

* **انتهاء التجربة** → إصدار أول فاتورة، والتحوّل إلى `past_due` بمهلة سداد.
* **انتهاء الفترة المدفوعة** → تجديد وإصدار فاتورة، أو إنهاء الاشتراك إن أُوقف التجديد.
* **الفواتير المتأخرة** → تذكير داخل المهلة، ثم توقّف الكتابة بعدها.

كل تحوّل يُشعر أصحاب صلاحية `billing.view` في الجهة عبر قنوات الإشعارات الثلاث.
يمكن تشغيل الدورة فوراً من اللوحة: `POST /api/platform/jobs/subscriptions/run`.

### الفواتير

رقم متسلسل على مستوى المنصة (`NOOR-2026-00001`)، وضريبة قيمة مضافة قابلة للضبط (١٥٪ افتراضاً)،
وطباعة رسمية مرَوَّسة بهوية المنصة مع الرقم الضريبي والسجل التجاري.

### السداد

الجهة تُبلغ عن تحويلها من شاشة الاشتراك (مع المرجع ومرفق الإيصال)، فيبقى الإشعار `pending`
حتى يعتمده مالك المنصة — عندها تُسدَّد الفاتورة ويعود الاشتراك `active` في عملية ذرّية واحدة.
هذا يناسب السوق المحلي (التحويل البنكي) ويترك بوابة الدفع الإلكتروني إضافةً لاحقة بلا تغيير
في نموذج البيانات.

### ما لا تفعله المنصة عند توقّف السداد

**لا تحجب البيانات ولا تمحوها.** توقف الكتابة فقط:

| الحالة | القراءة | الكتابة | شاشة السداد |
|---|---|---|---|
| نشط / تجريبي | ✔ | ✔ | ✔ |
| متأخر داخل المهلة | ✔ | ✔ | ✔ |
| متأخر بعد المهلة | ✔ | ✘ | ✔ |
| منتهٍ / ملغى | ✔ | ✘ | ✔ |
| موقوف إدارياً | ✔ | ✘ | ✔ |

المحو لا يقع إلا بأمر صريح من مالك المنصة مع تأكيد رمز الجهة.

## ٦. التخصيص الديناميكي وربط النطاقات

`GET /api/public/brand` يستنتج الجهة من ترويسة `Host`:

1. مطابقة `tenants.custom_domain` مباشرةً
2. وإلا مطابقة أول مقطع من النطاق مع `tenants.code` (نطاق فرعي)
3. وإلا هوية المنصة نفسها

شاشة الدخول تقرأ منه الاسم والشعار وتطبّق ألوان الجهة على متغيّرات CSS قبل الرسم — فيرى
منسوبو كل جهة هويتهم دون أي شيفرة خاصة بها.

على Cloudflare: أضف النطاق كـ Custom Domain للعامل، ثم اكتبه في حقل «النطاق المخصّص» بلوحة
الجهة. الشهادة تُصدر تلقائياً.

## ٧. الواجهات البرمجية

### عامة (بلا مصادقة) — `/api/public`

| المسار | الغرض |
|---|---|
| `GET /platform` | هوية المنصة وحالة التسجيل |
| `GET /brand` | هوية الجهة حسب النطاق |
| `GET /plans` | خطط الأسعار المعروضة |
| `GET /signup/availability?code=&email=` | فحص التوفر |
| `POST /signup` | إنشاء جهة جديدة |

### الجهة — `/api/billing` (صلاحية `billing.view` / `billing.manage`)

`GET /` · `GET /plans` · `POST /subscribe` · `POST /cancel` · `POST /resume` ·
`GET /invoices` · `GET /invoices/:id` · `GET /invoices/:id/print` · `POST /invoices/:id/declare-payment`

### مالك المنصة — `/api/platform`

`GET /overview` · جهات (`GET|POST /tenants`, `GET|PATCH|DELETE /tenants/:id`, `POST /tenants/:id/plan`,
`POST /tenants/:id/impersonate`) · خطط (`GET|POST /plans`, `PATCH|DELETE /plans/:id`) ·
اشتراكات وفواتير ومدفوعات · طلبات تسجيل · `GET|PUT /settings` · مالكون · `GET /logs` ·
`GET /jobs` و`POST /jobs/:name/run`

## ٨. الترقية من قاعدة قائمة

المخطط يضيف جداول جديدة وأعمدة على `tenants` و`users`. جُمل `CREATE TABLE IF NOT EXISTS`
لا تمسّ جدولاً موجوداً، لذلك يوجد **مُوفِّق أعمدة** (`server/core/upgrade.js`) يقرأ الأعمدة
الفعلية ويضيف الناقص فقط — آمن التكرار ويعمل على SQLite و D1 معاً.

```bash
# تشغيل ذاتي
npm run migrate && npm run seed      # يضيف الأعمدة والخطط وإعدادات المنصة

# Cloudflare
npm run cf:build && npm run cf:migrate
npm run cf:bootstrap -- https://‹نطاقك›
```

`npm run seed` على قاعدة معبّأة مسبقاً لا يمسّ بياناتها — يحدّث طبقة الـ SaaS فقط.

تطبيق الحدود فعلياً · حساب الضريبة والإجمالي · دورة التجربة والفاتورة والمهلة وتوقّف الكتابة ·
السداد وعودة الخدمة · الإيقاف الإداري وبقاء القراءة · إدارة الخطط · الدخول الإداري وتسجيله ·
طلبات المراجعة اليدوية · محو الجهة وبقاء أثره · العودة لوضع المستأجر الواحد.
