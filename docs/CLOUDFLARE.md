# النشر على Cloudflare

دليل تشغيل **منصة رقيم** بالكامل على بنية Cloudflare: الاستضافة والتشغيل على **Workers**،
قاعدة البيانات على **D1**، تخزين الملفات على **R2**، البثّ اللحظي على **Durable Objects**،
والوظائف المجدولة على **Cron Triggers** — بلا أي مزوّد خارجي.

---

## ١. لماذا شيفرة واحدة لبيئتين؟

وثيقة المتطلبات تشترط «مركزية التحديثات: مصدر شيفرة واحد يخدم جميع المستأجرين». لذلك لا يوجد
في المشروع نسختان من المنطق، بل **نواة مشتركة** ومحوّلان رفيعان لكل بيئة:

```
server/core/      ← كل المنطق: المسارات، الصلاحيات، التقارير، الإشعارات، الوظائف
   ├─ sql.js      ← عقد قاعدة البيانات غير المتزامن (get/all/run/batch/exec)
   ├─ crypto.js   ← JWT و PBKDF2 و HKDF بواجهة Web Crypto القياسية
   └─ webpush.js  ← RFC 8291 + RFC 8292 مكتوبتان بلا اعتماديات

server/node/      ← محوّل التشغيل الذاتي : better-sqlite3 · القرص · ws
server/worker/    ← محوّل Cloudflare      : D1 · R2 · Durable Object · Assets
```

النتيجة: **٦١٨ فحصاً وظيفياً + القناة اللحظية والوظائف المجدولة تمرّ بنجاح على البيئتين بالنتيجة نفسها.**

| القدرة | التشغيل الذاتي (Node) | Cloudflare |
|---|---|---|
| قاعدة البيانات | SQLite (better-sqlite3) | **D1** |
| تخزين الملفات | القرص المحلي | **R2** |
| الواجهة | Hono + خدمة ملفات ثابتة | **Workers Static Assets** |
| البثّ اللحظي | WebSocket (ws) | **Durable Object** (مع سبات) |
| الوظائف الدورية | `setInterval` | **Cron Triggers** |
| الطوابير | عامل داخل العملية | `waitUntil` + Cron، أو **Queues** |
| النسخ الاحتياطي | ملف SQLite + SQL مضغوط | SQL مضغوط إلى R2 + **D1 Time Travel** |

---

## ٢. المتطلبات

* حساب Cloudflare (الخطة **المجانية تكفي**: Workers + D1 + R2 + Durable Objects بتخزين SQLite).
* Node.js 20 فأحدث محلياً.
* تسجيل الدخول: `npx wrangler login`

> **R2** يتطلّب تفعيل الخدمة مرّة واحدة من لوحة التحكم (بطاقة دفع للتحقق فقط؛ هناك حصّة مجانية سخيّة).
> **Queues** وحدها تتطلّب خطة Workers Paid — وهي **اختيارية**؛ بدونها يعمل الطابور عبر `waitUntil` ومؤقّت Cron.

## ٣. خطوات النشر

### ٣.٠ الطريق القصير — أمر واحد

```bash
npx wrangler login          # أو:  export CLOUDFLARE_API_TOKEN=…
npm run cf:link
```

`cf:link` ينفّذ السلسلة كاملةً ويكتشف ما أُنشئ سابقاً فلا يكرّره:

| الخطوة | ما تفعله |
|---|---|
| ١ | تتحقّق من الدخول وتتوقّف فوراً برسالة صريحة إن لم يكن مضبوطاً |
| ٢–٣ | تنشئ قاعدة D1 (أو تكتشفها) **وتكتب معرّفها في `wrangler.toml` تلقائياً** |
| ٤ | تنشئ دلو R2 (أو تكتشفه) |
| ٥ | تولّد الأسرار الأربعة وترفعها، وتحفظ نسخةً في `.cf-secrets.json` (مُستبعَد من git) |
| ٦–٧ | تبني المخطط ورؤوس الأمان وتطبّق المخطط على D1 البعيدة |
| ٨–٩ | تنشر العامل، وتلتقط رابطه، وتضبط `APP_URL` عليه ثم تعيد النشر |
| ١٠ | تنفّذ التهيئة الأولى وتطبع حسابات الدخول |
| ١١ | تفحص `/api/health` وتؤكّد أن D1 و R2 وإشعارات الدفع تعمل |

```bash
npm run cf:link -- --dry      # يعرض الخطة وينفّذ الفحوص القرائية فعلاً دون تغيير شيء
npm run cf:link -- --rotate   # يعيد توليد الأسرار (يُبطل اشتراكات الإشعارات القائمة)
npm run cf:link -- --name رقيم-الرياض   # اسم عامل مختلف
```

> ⚠ احتفظ بـ `.cf-secrets.json`: مفتاحا VAPID لا يمكن استرجاعهما من Cloudflare،
> وتغييرهما يُبطل كل اشتراكات الإشعارات على أجهزة المستخدمين.

### ٣.٠-ب الطريق بلا وحدة طرفية — من المتصفّح وحده

كل الخطوات تُنفَّذ من لوحة Cloudflare ومحرّر GitHub على الويب:

| # | أين | ماذا |
|---|---|---|
| ١ | Cloudflare ← R2 | `Enable R2` (تُطلب بطاقة حتى في الحد المجاني) ثم `Create bucket` باسم `raqeem-files` |
| ٢ | Cloudflare ← Storage and Databases ← D1 | `Create database` باسم `raqeem-db`، وانسخ `Database ID` |
| ٣ | GitHub ← `wrangler.toml` ← ✏️ | الصق المعرّف في `database_id` (السطر ٣١) ثم `Commit changes` |
| ٤ | Cloudflare ← Workers & Pages | `Create` ← `Import a repository` ← اختر المستودع والفرع `main` |
| ٥ | العامل ← Settings ← Variables and Secrets | أضِف الأسرار الأربعة **من نوع Secret**: `JWT_SECRET` · `VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY` · `BOOTSTRAP_TOKEN` |
| ٦ | المتصفّح | افتح `https://‹رابطك›/__bootstrap` والصق رمز التهيئة واضغط الزر |
| ٧ | GitHub ← `wrangler.toml` | اضبط `APP_URL` (السطر ٧٠) على رابطك، والحفظ يُعيد النشر تلقائياً |

**لا حاجة لتطبيق المخطط يدوياً**: صفحة `/__bootstrap` تنشئ الجداول الـ ٦٠ وتعبّئ الجهة
رقم ١ في خطوة واحدة. وهي محميّة برمز التهيئة، ولا تعمل ما لم يُضبط السرّ.

بعد نجاحها: غيّر كلمات المرور الافتراضية، ثم **احذف السرّ `BOOTSTRAP_TOKEN`** من
إعدادات العامل فتتعطّل الصفحة نهائياً.

---

أمّا ما يلي فهو التفصيل اليدوي لكل خطوة، لمن أراد التحكّم الدقيق أو التشخيص.

### ٣.١ إنشاء الموارد

```bash
npx wrangler d1 create raqeem-db          # انسخ database_id من الناتج
npx wrangler r2 bucket create raqeem-files
```

ضع `database_id` في `wrangler.toml`:

```toml
[[d1_databases]]
binding = "DB"
database_name = "raqeem-db"
database_id = "‹المعرّف الذي ظهر لك›"
```

### ٣.٢ ضبط الأسرار

```bash
npm run cf:secrets            # يولّد القيم ويعرض الأوامر
npm run cf:secrets -- --put   # أو يرفعها مباشرةً
```

الأسرار المطلوبة:

| السرّ | الغرض |
|---|---|
| `JWT_SECRET` | توقيع الجلسات — سلسلة عشوائية طويلة |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | إشعارات الدفع للمتصفح والجوال |
| `BOOTSTRAP_TOKEN` | يحمي مسار التهيئة `/__bootstrap` |

> ⚠ احتفظ بمفتاحَي VAPID: تغييرهما يُبطل كل اشتراكات الإشعارات القائمة على أجهزة المستخدمين.

### ٣.٣ إنشاء المخطط والنشر

```bash
npm run cf:build      # يولّد migrations/0001_init.sql و web/_headers من مصدرهما
npm run cf:migrate    # يطبّق المخطط على D1 (١١٢ جملة تشمل ١٣ مُشغّل حماية)
npm run cf:deploy     # ينشر العامل والواجهة
```

### ٣.٤ التهيئة الأولى

```bash
npm run cf:bootstrap -- https://raqeem-erp.‹حسابك›.workers.dev
```

يطبّق المخطط (إن لم يكن مطبّقاً) ويُنشئ الجهة رقم ١ بأدوارها الـ ١٠ وصلاحياتها الـ ٦٠ وبياناتها،
ويعبّئ خطط الاشتراك وإعدادات المنصة (طبقة الـ SaaS تبقى معطّلة حتى يفتحها الادمن).

ويُنشئ معها **حساب إدارة المنصة** المستقل — لا ينتمي لأي مجمّع:

| اللوحة | الرابط | الحساب الأولي |
|---|---|---|
| تطبيق المجمّع | `/` | `admin@riyadh-qu.sa` / `Admin@123` |
| إدارة المنصة | `/admin` | `admin@raqeem.sa` / `Admin@123` |

**غيّر كلمات المرور الافتراضية فوراً بعد أول دخول** — من `/settings` للمجمّع، ومن لوحة المنصة
لحساب الادمن. وفعّل التحقّق بخطوتين على حساب الادمن: هو الطبقة الوحيدة التي تتجاوز عزل الجهات.

### ٣.٥ نطاق مخصّص

من لوحة التحكم: **Workers & Pages ← raqeem-erp ← Settings ← Domains & Routes ← Add Custom Domain**،
ثم اضبط `APP_URL` في `[vars]` داخل `wrangler.toml` وأعد النشر. الشهادة تُصدَر تلقائياً، و**HTTPS شرط
لعمل عامل الخدمة وإشعارات الدفع والموقع الجغرافي**.

## ٥. تفاصيل البنية

### قاعدة البيانات D1

* المخطط مصدره الوحيد `server/core/schema.sql`؛ يُولَّد منه ملف الترحيل بـ `npm run cf:build:migrations`.
* D1 لا يدعم المعاملات التفاعلية، لذا كل كتابة متعدّدة الجمل مُعادة الصياغة على `db.batch()` — وهي
  ذرّية على البيئتين.
* مُشغّلات الحماية (سجل تدقيق غير قابل للتعديل، وقفل الفصول المؤرشفة) تعمل داخل D1 كما هي.

### تخزين R2

كل ملف يُحفظ تحت `tenants/{tenant_id}/…` تحقيقاً لشرط عزل التخزين في المقدمة الاستراتيجية.
الملفات تُقدَّم عبر المنصة (لا روابط عامة) فتبقى محكومة بالصلاحيات وسجل التدقيق.

### البثّ اللحظي (Durable Object)

كائن دائم واحد لكل جهة تعليمية `tenant:{id}`، يستخدم **واجهة السبات** فلا يُحتسب وقت المعالجة
أثناء انتظار الرسائل. الترقية إلى WebSocket تمرّ أولاً بالعامل الذي يتحقّق من رمز الجلسة، فلا
يصل إلى الكائن الدائم اتصال غير موثّق.

إن لم يكن الربط `HUB` متاحاً، تعود واجهة البثّ `null` ويتحوّل العميل تلقائياً إلى **الاستطلاع
الدوري** كل ٢٠ ثانية — فتستمر الإشعارات والمحادثات دون أي خطأ للمستخدم.

### الوظائف المجدولة

| الجدول (UTC) | الوظيفة |
|---|---|
| `*/5 * * * *` | تصريف طابور المعالجة الخلفية وإعادة العالق |
| `*/15 * * * *` | تصعيد تذاكر الدعم المتجاوزة لاتفاقية مستوى الخدمة |
| `0 * * * *` | إعادة احتساب مؤشرات الأداء |
| `0 3 * * *` | تذكير المهام المستحقة (٦ صباحاً بتوقيت الرياض) |
| `0 2 * * *` | النسخ الاحتياطي اليومي إلى R2 (٥ صباحاً بتوقيت الرياض) |
| `0 1 * * *` | دورة الاشتراكات والفوترة — المرحلة الثانية (٤ صباحاً بتوقيت الرياض) |
| `0 0 * * *` | لقطة مؤشرات المنصة وتقليم سجلَّي التشغيل والدخول (٣ صباحاً بتوقيت الرياض) |

كل تشغيل — مجدولاً كان أو يدوياً — يُكتب في `job_runs` بحالته ومدّته وناتجه أو نص خطئه،
ويظهر في شاشة **التشغيل** بلوحة إدارة المنصة (`/admin/ops`)، فلا تمرّ وظيفة فاشلة دون أن تُرى.

لتجربتها محلياً: `curl "localhost:8787/cdn-cgi/handler/scheduled?cron=0+2+*+*+*"`

### الطوابير (اختياري)

مع خطة Workers Paid، أزل التعليق عن قسم `queues` في `wrangler.toml` ثم:

```bash
npx wrangler queues create raqeem-jobs
```

تُلتقط الوحدة تلقائياً: `enqueue()` يرسل إلى الطابور بدل الاعتماد على `waitUntil`.

### طبقة الـ SaaS (المرحلة الثانية)

مبنيّة بالكامل ومعطّلة افتراضياً. تشغيلها على Cloudflare لا يحتاج أي ربط إضافي — الجداول
ضمن المخطط نفسه على D1، ودورة الفوترة على مؤقّت Cron. عند فتحها:

* أضف نطاق كل جهة كـ **Custom Domain** للعامل، ثم اكتبه في حقل «النطاق المخصّص» بلوحة الجهة
  ليعمل التخصيص الديناميكي (`GET /api/public/brand` يستنتج الجهة من ترويسة `Host`).
* راجع **[docs/SAAS.md](SAAS.md)** لتفاصيل الخطط والفوترة ولوحة إدارة المنصة.

**المستويات الأربعة فوقها تعمل على Cloudflare دون أي مزوّد خارجي:**

| القدرة | كيف تعمل هنا |
|---|---|
| الفاتورة الإلكترونية (ZATCA) | رمز QR ومستند UBL وسلسلة التجزئة مبنيّة بـ Web Crypto وحدها؛ المستند يُحفظ في **R2** تحت `tenants/{id}/einvoices/` |
| التحقّق بخطوتين (TOTP) | HMAC-SHA1 عبر Web Crypto — بلا `node:crypto` ولا مكتبة خارجية |
| تصدير بيانات جهة | يُنتَج SQL ويُضغط بـ `CompressionStream('deflate-raw')` بدل `node:zlib` |
| لقطات المؤشرات | مؤقّت Cron اليومي `0 0 * * *` يكتب في `platform_metrics` على D1 |
| بوابة الدفع | إشعار البوابة يصل إلى `POST /api/webhooks/payments` — مسار مفتوح على العامل نفسه |

المفتاح السرّي للبوابة يُحفظ في `platform_settings` ولا يُرسَل إلى واجهة الجهة إطلاقاً؛
وإن فضّلت إبقاءه خارج القاعدة فارفعه سرّاً بـ `npx wrangler secret put`.

### التطبيق المثبَّت (PWA) دون اتصال — فخّان خاصان بـ Cloudflare

واجه البناءُ فرقاً حقيقياً بين البيئتين هنا، ومُعالَجٌ في `web/sw.js`:

**١. إعادة توجيه `/index.html`.** تُعيد Cloudflare Static Assets توجيه `/index.html`
إلى `/` بالرمز ٣٠٧. فحين يخزّن عامل الخدمة هيكل التطبيق، تُحفَظ الاستجابة وعلَمها
`redirected = true` — والمتصفّح **يرفض** استجابةً موجَّهة داخل `respondWith` لطلب تنقّل،
فيسقط التنقّل كلياً (`ERR_FAILED`) بدل أن يُخدَم الهيكل المخزّن. العلاج: إعادة بناء
الاستجابة (`cleanCopy`) قبل تخزينها وقبل خدمتها، فيسقط العلَم.

**٢. التحميل المسبق للتنقّل (Navigation Preload).** حين يكون مُفعَّلاً وينقطع الاتصال،
يُجهض المتصفّح التنقّل **قبل** أن يصل حدث `fetch` إلى عامل الخدمة أصلاً — فلا يُخدَم شيء.
عُطِّل عمداً: مكسبه ضئيل في تطبيق صفحة واحدة لا يقع فيه تنقّل كامل بعد الإقلاع،
والعمل دون اتصال أولى من توفير جولة شبكة واحدة.

يحرس الحالتين فحصان دائمان في `npm run verify` (القسم ١٨) وفحص متصفّح يتنقّل دون اتصال
على `/` و`/tasks` و`/index.html` و`/billing` و`/admin` على البيئتين.

### النسخ الاحتياطي

* **تلقائي**: كل يوم إلى R2 تحت `tenants/{id}/backups/` (يُحتفظ بآخر `BACKUP_KEEP` نسخة).
* **يدوي**: من الإعدادات ← 💾 النسخ الاحتياطي، أو `POST /api/org/backups`.
* **الاستعادة**:

```bash
npx wrangler r2 object get raqeem-files/tenants/1/backups/raqeem-2026-01-01-02-00-00.sql.gz --file b.sql.gz
gunzip b.sql.gz
npx wrangler d1 execute raqeem-db --remote --file=b.sql
```

الملف يُسقط مُشغّلات الحماية قبل الإدراج ويعيد إنشاءها بعده، فالاستعادة تعمل كما هي.
إضافةً إلى ذلك يوفّر D1 **Time Travel** للرجوع بالقاعدة إلى أي لحظة خلال ٣٠ يوماً:

```bash
npx wrangler d1 time-travel restore raqeem-db --timestamp=2026-01-01T00:00:00Z
```

## ٦. المتغيّرات

غير السرّية تُضبط في `[vars]` داخل `wrangler.toml`:

| المتغيّر | القيمة الافتراضية | الوصف |
|---|---|---|
| `NODE_ENV` | `production` | يفعّل رأس HSTS ويُخفي تفاصيل الأخطاء |
| `APP_URL` | — | العنوان العام (يُستعمل في روابط الإشعارات) |
| `VAPID_SUBJECT` | `mailto:…` | جهة الاتصال في رأس VAPID |
| `GEOFENCE_DEFAULT_RADIUS` | `50` | نطاق التحضير الذكي بالمتر |
| `UPLOAD_MAX_MB` | `15` | أقصى حجم للمرفق |
| `RATE_LIMIT_MAX` | `300` | طلبات/دقيقة لكل مستخدم |
| `PUBLIC_API_RATE_LIMIT_MAX` | `120` | طلبات/دقيقة للواجهة العامة |
| `LOGIN_ACCOUNT_MAX` | `8` | محاولات دخول فاشلة لكل حساب قبل الإيقاف المؤقّت |
| `BACKUP_ENABLED` / `BACKUP_KEEP` | `true` / `14` | النسخ الاحتياطي اليومي وعدد النسخ المحفوظة |

## ٧. المتابعة والتشخيص

```bash
npm run cf:tail                              # سجلّ حيّ من الإنتاج
curl https://‹نطاقك›/api/health              # حالة الخدمة والمزوّدات المربوطة
```
